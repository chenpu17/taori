# P1：运行过程可观测（Run Timeline）

Date: 2026-05-03
Status: P1 implemented

## 定位

Run Timeline 面向真实使用后的复盘：用户不只看到模型最终回答，还能看到这一轮对话用了什么上下文、调用了哪个模型、哪些工具参与、是否失败、成本是否已记录。

它服务于 Taori 的定位：多模型桌面 AI 工作编排助手。首版只增强透明度和信任，不自动替用户决定基础聊天模型。

## 用户价值

- 多轮会话后，用户可以解释“为什么这次回答会这样”。
- 多工具混合时，用户能确认工具是否真的被调用、是否成功、耗时如何。
- 多模型切换后，用户能复盘某一轮对应的模型和成本。
- 出错时，用户能区分模型失败、工具失败、用户停止、成本缺失等不同状态。

## 首版范围

- 会话条新增“运行过程”入口。
- 按会话查询最近运行事件，按单次 run 分组展示。
- 覆盖聊天回合、上下文快照、模型调用、工具调用、成本记录、能力路由和回合结束状态。
- 事件随会话持久化，刷新后仍可查看。

## 不做

- 不做自动动态模型路由。
- 不做长期后台任务队列。
- 不做复杂 DAG/workflow 编辑器。
- 不把完整 prompt、附件原文、图片 base64 写入运行事件。

## 验收场景

1. 用户发起普通聊天，打开运行过程，应看到回合开始、上下文快照、模型开始/完成、成本记录、回合完成。
2. 用户用工具模型生成图片，打开运行过程，应看到图像工具 start/finish 事件。
3. 用户关闭会话工具后发起需要联网的请求，运行过程应反映该轮上下文中工具不可用。
4. 用户切换模型做第二轮总结，运行过程应按新的 run 分组展示模型与成本。
5. 用户刷新页面后重新进入会话，运行过程仍可查询。

## 后续候选

- 将 roundtable 回合纳入同一 Run Timeline。
- 支持从运行过程跳到对应消息、工具结果、成本记录。
- 增加失败尝试链路：候选模型、失败分类、用户最终选择。
- 为未来 workflow/approval 提供统一事件基座。
