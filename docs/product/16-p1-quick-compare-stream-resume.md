# 16 · P1 Quick Compare 与断流续接

Status: draft  
Owner: Taori  
Date: 2026-05-06

## 1. 产品目标

P0 已完成成本可信与长期记忆底座。P1 的目标是让用户在高频聊天中更“爽”：

1. **Quick Compare**：用户不必进入完整圆桌，也能一键让 3 个模型并行回答同一个问题，快速比较风格、质量和成本。
2. **断流续接**：SSE 或网络中断时，Taori 不把用户丢在半截回复里，而是识别 incomplete run，自动或半自动续接，减少“内容和费用白丢”的挫败感。

这两个能力都服务于同一个体验原则：**模型很多，但用户不应承担编排、恢复和判断的复杂度。**

## 2. Quick Compare

### 2.1 用户故事

- 作为用户，我在输入框旁点击“一键对比”，Taori 自动选择 3 个合适模型并行回答当前问题。
- 作为用户，我希望对比结果就在当前聊天上下文中出现，不强迫我进入完整圆桌流程。
- 作为用户，我能看到每个模型的成本、耗时、首 token、失败状态，并能把其中一个回答采纳为本轮正式回复。
- 作为用户，如果某个模型失败，其他模型仍继续完成；失败卡片给出换模型或重试建议。

### 2.2 交互形态

入口：

- Composer 发送按钮旁新增 `对比` 按钮。
- 当输入较短、开放性强、或当前模型历史质量反馈不稳定时，Quick Action 可提示“用 3 个模型对比一下”。

结果展示：

- 当前会话中新增一张 `QuickCompareCard`，包含 3 列回答。
- 每列显示：
  - 模型名 / Provider
  - 流式内容
  - 状态：生成中 / 完成 / 失败 / 已采纳
  - 成本、首 token、总耗时
  - 操作：采纳为回复、继续用此模型聊、重试此列
- 卡片底部显示总成本与“升级为圆桌讨论”入口。

采纳行为：

- 默认 Quick Compare 不直接把 3 条回答都写成普通 assistant 消息。
- 用户点击“采纳”后，Sidecar 将对应输出提升为本轮正式 assistant 消息，后续上下文只带被采纳回答。
- 未采纳输出仍作为 compare artifact 可在历史卡片中查看，但不污染后续 LLM 上下文。

### 2.3 选模策略

首版默认选 3 个 chat 模型：

1. 当前选中模型。
2. 一个低成本快模型。
3. 一个质量/推理能力更强的模型。

过滤规则：

- 排除 disabled、demoted 且不可自动选中的模型。
- 排除无 provider、无 key、非 chat capability 的模型。
- 若不足 3 个可用模型，则显示实际数量并提示原因。

### 2.4 不做

- 不做完整圆桌 analyzer / summarizer。
- 不做多轮互见反驳。
- 不默认生成综合总结；总结可作为后续“升级为圆桌”或“让当前模型综合”动作。
- 不把所有 compare 输出都送入后续上下文。

## 3. 断流续接

### 3.1 用户故事

- 作为用户，如果生成过程中网络断开或页面刷新，我重新进入会话后能看到“这条回复未完成，可续接”。
- 作为用户，我可以开启自动续接；断流后 Taori 尽量自动继续，不需要我重新组织上下文。
- 作为用户，我能知道续接产生了新成本，且预算硬上限仍会阻断。

### 3.2 状态表现

消息状态：

- `streaming`：正在生成。
- `incomplete`：服务端已保存部分内容，但生成未自然结束。
- `complete`：正常完成。
- `failed`：上游明确失败。

UI 行为：

- 当前 stream 异常结束且没有收到完成帧时，前端先显示“正在确认是否可续接”。
- Sidecar 查询到 assistant message 为 `incomplete` 后：
  - 自动续接开启：显示“正在续接上次回答”，调用 continue。
  - 自动续接关闭：显示决策条“继续生成 / 换模型续接 / 放弃并保留已生成内容”。
- 页面刷新后重新打开会话，也应根据历史消息 `status='incomplete'` 显示续接入口。

### 3.3 续接原则

- 续接必须由 Sidecar 基于 run/message 状态决定，Renderer 不能只凭前端内存判断。
- 续接使用现有 `/v1/runs/:id/continue` 语义：把已有 assistant 内容作为上下文，并追加“不要重复，从中断处继续”的指令。
- 续接产生新 assistant message，`parent_message_id` 指向 incomplete message；UI 可折叠显示为同一回复链。
- 成本独立记录，但 Run Timeline 应标明 `parent_run_id` 和 `continued_from_message_id`。
- 硬预算、模型可用性、记忆召回、Persona、工具策略都必须与普通 chat 保持一致。

### 3.4 不做

- 不做字节级 SSE 重放；AI SDK data-stream 不是事件日志，首版不保证恢复到最后一个 token。
- 不把断流续接伪装成同一次模型调用；它是一次新的调用，应透明记录成本。
- 不默认跨设备续接实时 stream；只保证本地 Sidecar 持久化状态可恢复。

## 4. 验收标准

### Quick Compare

- 用户可从 composer 一键启动 2-3 个模型并行回答。
- 任意单列失败不影响其他列完成。
- 每列有成本、耗时、失败原因或完成状态。
- 用户采纳某列后，后续聊天上下文只包含被采纳输出。
- Run Timeline 可看到 compare 启动、各 participant、成本与采纳事件。

### 断流续接

- 用户点击停止或连接中断后，Sidecar 能持久化 incomplete message。
- 刷新页面后仍能看到续接入口。
- 自动续接开启时，前端可自动调用 continue，但硬预算超限时必须停下并提示。
- 续接结果与原 incomplete 回复在 UI 上形成清晰的父子关系。
- Run Timeline 可追踪原 run、续接 run、成本记录与最终状态。
