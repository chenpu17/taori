# 17 · P2 轻量 RAG 预备层

Status: draft  
Owner: Taori  
Date: 2026-05-06

## 1. 产品目标

当前文件能力已经能读取文本/PDF，但主要问题是：**长文件会被整段塞进上下文，既贵、又慢、还容易挤掉真正相关的历史消息。**

P2 轻量 RAG 预备层的目标不是马上做完整知识库，而是先把文件能力升级成“按问题检索片段”：

- 用户拖入长文档后，Taori 能只取与问题相关的片段。
- 回答中能展示引用片段来源，让用户知道依据来自哪里。
- 默认完全本地：先用 SQLite FTS/BM25，不依赖外部 embedding。
- 为后续本地 embedding、跨会话引用、项目知识库预留接口。

## 2. 用户故事

- 作为用户，我拖入一份几十页 PDF，问其中某个细节，Taori 不应该把全文塞进模型，而应检索相关片段回答。
- 作为用户，我希望回答里能看到“引用了哪个文件、哪个片段”，方便核查。
- 作为用户，我不想因为上传了大文件就让上下文窗口爆掉或费用突然变高。
- 作为用户，我希望敏感项目文件默认留在本地，不被发送去外部 embedding 服务。

## 3. 用户体验

### 3.1 附件进入会话

用户拖入 PDF / Markdown / TXT / JSON：

1. Sidecar 抽取文本。
2. 生成 file chunks 并写入 SQLite FTS。
3. UI 显示“已索引 N 个片段，可按问题检索”。

如果文件无法解析：

- 显示明确原因：扫描件 PDF、编码异常、文件过大或不支持 mime。
- 不静默失败。

### 3.2 问答时检索

当用户问题涉及附件或会话文件：

- Taori 先用用户问题搜索当前会话相关 chunks。
- 只把 top K 片段放入 system/context。
- 回答末尾展示引用：
  - 文件名
  - 片段序号
  - 简短摘录

### 3.3 文件工具升级

现有 `file_read` 保留，但定位变成“显式读文件全文/长片段”的工具。新增首选能力：

- `file_search`：按问题检索文件片段。

模型工具说明应鼓励：

- 对长文件、多个附件、定位问题，优先用 `file_search`。
- 只有用户明确要求“阅读全文/完整内容”时才使用 `file_read`。

## 4. 不做

- 不默认调用外部 embedding。
- 不做跨设备云知识库。
- 不做复杂权限系统；仍以本地 Sidecar 与会话归属为边界。
- 不承诺扫描件 OCR；OCR 可作为后续本地能力。
- 不把所有历史会话都默认纳入检索；跨会话引用后续通过 `@项目` / `@会话` 显式触发。

## 5. 验收标准

- 上传或读取文本/PDF 后，Sidecar 能生成 chunk 并写入本地索引。
- 对同一文件提问时，模型上下文只包含 top K 相关片段，而不是全文。
- 回答中可展示引用来源。
- `file_read` 仍可工作，旧路径不破坏。
- 无 embedding 配置时功能完整可用。
- FTS 查询、chunk 生成、上下文注入有单测或路由测试覆盖。
