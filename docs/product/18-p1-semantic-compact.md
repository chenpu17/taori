# 18 · P1 语义压缩升级

Status: draft  
Owner: Taori

## 1. 产品目标

当前 `compact_context` 已能在恢复失败请求时做确定性摘要，但它本质是“截断 + 拼接”，只能保证安全，不保证信息密度。P1 语义压缩升级的目标是：

1. **让长对话继续可用**：用户不需要手动删历史，也能在长会话里继续获得连贯回答。
2. **让压缩可信透明**：用户能看到压缩了哪些历史、压缩比例、是否用了模型、产生了多少成本。
3. **让隐私可控**：默认保留确定性压缩；语义压缩必须可关闭，并可选择只用本地/低成本模型。

## 2. 用户故事

- 作为用户，当上下文快满时，Taori 主动提示“可压缩较早历史后继续”，而不是直接丢上下文或让上游报错。
- 作为用户，我能选择“安全确定性压缩”或“语义压缩”，并知道语义压缩会产生一次额外模型调用。
- 作为用户，我能在 Run Timeline 看到摘要来源、压缩比例、摘要模型、成本和是否本地处理。
- 作为用户，如果语义压缩失败，Taori 应回退到确定性压缩或明确提示，而不是静默丢历史。

## 3. 交互与默认策略

入口：

- 失败恢复卡：现有“压缩上下文后重试”保留，增加“语义压缩”选项。
- 上下文预警卡：当 `context_snapshot` 显示裁剪较多历史时，提示“下次可启用语义压缩”。
- 设置页：新增“上下文压缩”设置：
  - 默认模式：确定性 / 语义（低成本模型）/ 本地优先。
  - 摘要模型：自动选择或手动指定。
  - 最大摘要 token：默认 800。

默认：

- 首版默认仍使用确定性压缩，避免额外成本与隐私惊吓。
- 语义压缩作为显式用户动作或设置项启用。
- 如果启用硬预算且语义压缩预估超限，直接阻断，不允许借恢复流程绕过。

## 4. 可见性要求

每次压缩必须写入 Run Timeline：

- 压缩模式：`deterministic` / `semantic`。
- 来源范围：消息数、最早/最晚 message id。
- 压缩比例：原始估算 tokens、摘要 tokens。
- 摘要模型：model id / provider / 是否本地。
- 成本：关联 cost record。
- 回退：语义失败时是否回退到确定性压缩。

## 5. 不做

- 不在首版做长期知识库合并；语义压缩只服务当前会话上下文。
- 不默认把摘要写入长期记忆；如要沉淀，必须走记忆透明化链路。
- 不引入外部 embedding；这与 P2 RAG 分开。
- 不对所有历史自动后台压缩；只在用户动作或上下文风险触发时执行。

## 6. 验收标准

- 用户可在恢复动作中选择确定性或语义压缩。
- 语义压缩走统一预算守卫和成本记录。
- 压缩摘要进入本次上游上下文，但不伪装成用户新消息。
- Run Timeline 展示压缩来源、比例、模型、成本和失败/回退状态。
- 语义压缩失败时，用户能看到明确失败原因；可回退确定性压缩。
